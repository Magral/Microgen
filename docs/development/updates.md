# Обновления Microgen 1.0 — историческая техническая запись

> Этот документ описывает прежнюю реализацию механизма обновления. Он не подтверждает наличие такого же механизма в текущей версии Microgen на Defold. Перед изменением системы обновлений необходимо проверить фактический код Defold.

В главном меню прежней версии была доступна явная проверка обновлений. Создание сервиса, открытие меню и игровой процесс не вызывали сетевых запросов. Фонового обновления и автоматической проверки при запуске не было. Проверка обращалась по HTTPS к `https://api.github.com/repos/Magral/Microgen/releases/latest`, принимала только опубликованный релиз с числовой версией в формате `vMAJOR.MINOR.PATCH` или `MAJOR.MINOR.PATCH`, затем загружала из этого релиза файл `microgen-update.json`. Предложение обновления появлялось только при увеличении и семантической версии, и номера версии Android.

Для каждого запроса устанавливался тайм-аут 15 секунд, допускалось не более пяти перенаправлений, а размер тела ответа ограничивался (1 МиБ для метаданных релиза, 64 КиБ для манифеста). Отмена останавливала запрос. Ошибки и ограничения частоты запросов API показывались с явной кнопкой повтора; игра оставалась доступной без сети. Автоматических повторов и постоянного сетевого кэша не было.

Допускались только заранее заданные репозиторий и тег релиза. URL APK должен был вести по HTTPS на страницу загрузки GitHub Release в репозитории `Magral/Microgen`, соответствовать выбранному тегу, иметь безопасное имя файла с расширением `.apk` и присутствовать в списке вложений этого релиза. Другие хосты, репозитории, HTTP, строки запроса, фрагменты, закодированные пути и обход каталогов отклонялись. Такая проверка подтверждала происхождение релиза и согласованность метаданных, но не являлась криптографической подписью и не защищала от компрометации учётной записи издателя.

## Манифест релиза

В каждый стабильный релиз GitHub вместе с APK прикладывался файл `microgen-update.json`, сформированный по итоговому подписанному APK. Пример схемы (размер и хэш в примере необходимо заменять фактически измеренными значениями):

```json
{
  "version": "1.0.0",
  "version_code": 100,
  "apk_url": "https://github.com/Magral/Microgen/releases/download/v1.0.0/Microgen.apk",
  "size_bytes": 12345678,
  "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
}
```

Поле `version` должно было численно соответствовать тегу релиза. `version_code` — целое число от 1 до 2100000000. `size_bytes` — положительное целое число не более 512 МиБ. `sha256` — ровно 64 шестнадцатеричных символа. Отсутствующие или некорректные метаданные приводили к отказу. Старые релизы без манифеста можно было просматривать через проверенную страницу GitHub Release.

APK загружался через браузер. Приложение не скачивало APK самостоятельно и не проверяло байты загруженного файла по хэшу из манифеста; дайджест проверялся только как метаданные. Передачу ссылки браузеру нельзя описывать как загрузку внутри приложения с проверкой контрольной суммы или как автоматическую установку.

## Граница установки Android

Действие «Скачать APK через браузер» открывало проверенный URL вложения. Затем пользователь самостоятельно открывал загруженный APK и подтверждал установку в интерфейсе Android. Android мог потребовать разрешить установку из этого браузера или файлового менеджера. Приложение не устанавливало APK скрытно, не запускало локальный APK через `file://` и не запрашивало привилегии установщика.

Прежний механизм не являлся прямым установщиком. Для реализации прямой установки потребовалась бы отдельно проверенная интеграция Android: доступный URI `content://` с временными правами чтения, соответствующие разрешения/настройки установки пакетов и обработка результата PackageInstaller и подтверждения пользователя. Простая локальная загрузка и открытие пути к файлу не обеспечили бы поддерживаемый сценарий установки Android.

Идентификатор Android-пакета и ключ подписи должны совпадать с установленным приложением, а номер `version/code` — увеличиваться при каждом обновлении. Несовпадающий сертификат подписи обычно не позволяет обновить существующую установку. Нельзя советовать удалять приложение для обхода ошибки подписи: удаление может стереть локальные сохранения. Существующий keystore следует хранить в безопасном месте.

Для проверки GitHub при экспорте требовалось разрешение `permissions/internet=true`. Для передачи APK браузеру не требовались `REQUEST_INSTALL_PACKAGES` и разрешения на общую память. Значения `application/config/version` и `application/config/version_code` в `project.godot` должны были совпадать с версией/кодом профиля экспорта Android и манифеста релиза.

## Интеграция и тесты прежней версии

`core/update_feed.gd` представлял собой узел с сигналом `state_changed` и методами `check_updates()`, `cancel()`, `open_download()`, `open_release()`. Ключи состояния включали `status` (`idle`, `checking`, `available`, `current`, `error`), `newest`, `download_url`, `release_url` и `error`. Сервис использовался только из меню. Ожидающие запросы отменялись при выходе с экрана обновления или начале игры. Ошибка открытия браузера отображалась как ошибка сервиса.

`ui/update_view.gd.populate(hud, box, service, callbacks)` формировал русскоязычное содержимое меню. Необязательные обратные вызовы: `check`, `cancel`, `open_download`, `open_release`, `back`; методы сервиса предоставляли значения по умолчанию, кроме `back`. Перерисовка по `state_changed` выполнялась только при активном экране обновления.

В прежней версии тесты использовали имитацию сетевого обмена без публичных сетевых запросов и проверяли числовое сравнение версий, некорректные данные, исключение предварительных/черновых релизов, отклонение чужих репозиториев и URL, проверку манифеста и номера версии, отсутствие вложений, тайм-аут, HTTP-ошибку, повтор, отмену и успешную двухэтапную проверку. Загрузка через браузер, подтверждение установки и сохранность данных после обновления подписанной сборки требовали отдельной приёмки на реальном Android-устройстве.
