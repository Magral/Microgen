# Профиль производительности 1.4.0

Замер сделан 19 ноября 2026 на одной Linux-среде с Godot 4.6.3. База — исходники опубликованной 1.3.0 (`a558cfc`, идентичное дерево релиза). Кандидат — код симуляции и отрисовки 1.4.0 (`07b7d42`). Команда: `python3 tools/performance/run_profile.py --commit <ревизия> --output <каталог>`. Сценарий использует seed 44 и 36 000 шагов по 1/60 с. Спавн босса отключён для одинаковой нагрузки.

| Конец отрезка, с | Средний шаг 1.3 → 1.4, мс | p95 шага 1.3 → 1.4, мс | Память 1.3 → 1.4, МБ |
| ---: | ---: | ---: | ---: |
| 180 | 1,750 → 1,711 | 2,685 → 2,510 | 23,81 → 23,87 |
| 360 | 2,474 → 2,443 | 3,661 → 3,918 | 24,10 → 24,15 |
| 540 | 2,822 → 2,788 | 4,171 → 4,180 | 24,21 → 24,27 |
| 600 | 2,742 → 2,624 | 4,221 → 4,219 | 24,00 → 24,06 |

Среднее по всем шагам снизилось с 2,388 до 2,345 мс, примерно на 1,8%. При этом на одном отрезке p95 вырос примерно на 7%. Расход памяти на последнем срезе практически тот же. После нормализации идентификатора забега и исключения нового пустого поля награды контрольные точки совпали, включая положение объектов, случайное состояние и итоговые 247 убийств.

- Проходимость использует одну или две вычисленные координаты клеток вместо четырёх и читает каждую угловую клетку только один раз. Отдельный промежуточный прогон с одним этим изменением дал смешанные результаты по полному шагу. Суммарное время обновления фрагментов в финальном парном прогоне — 398 → 327 мкс на шаг.
- Для пустых и полностью вражеских залпов индекс целей теперь не строится. Суммарное время обновления снарядов — 19,7 → 4,5 мкс на шаг в этом сценарии. Снаряды вне видимой области также пропускаются при отрисовке.

## Боевые сценарии

Отдельно проверены три 20-секундные симуляции по 1200 шагов на seed 43, 44 и 45. Амёба стоит в 225 единицах от начальной точки босса. Подкрепления отключены, запас здоровья увеличен для полного прогона. В 1.3 на каждом seed одновременно бывало до 20 снарядов. В 1.4 пики составили 3, 7 и 12, каждый вариант предупредил о пяти залпах. Эти сценарии сравнивают разные атаки и показывают нагрузку от новых правил боя.

## Отрисовка

Обе версии воспроизводили одни и те же сохранения в 1280×720 через OpenGL Compatibility с Mesa llvmpipe. На сцену отведено 60 кадров прогрева и 180 измерений. Стресс-сцена с заполненными лимитами оценивается отдельно.

| Сохранение | Среднее время подготовки отрисовки 1.3 → 1.4, мс | p95 полного кадра 1.3 → 1.4, мс |
| --- | ---: | ---: |
| Старт | 22,67 → 20,87 | 116,78 → 99,07 |
| 180 с | 31,58 → 41,12 | 116,53 → 165,36 |
| 360 с | 34,47 → 38,47 | 129,20 → 140,92 |
| 600 с | 68,85 → 70,51 | 211,53 → 232,06 |
| Стресс-сцена | 189,28 → 223,92 | 509,31 → 887,65 |

Графическая часть в этом парном прогоне стала тяжелее в большинстве сцен. Кэш и число объектов на одинаковых сохранениях совпали, а многие неизменённые участки рисования тоже заняли больше времени. Причину разницы этот прогон не изолирует. В стресс-сцене было до 28 врагов, 80 полей, 96 останков, 600 объектов добычи и 200 снарядов. Она служит верхней проверкой нагрузки; обычный забег редко совпадает со всеми этими максимумами.

Результаты относятся к настольному CPU и программному OpenGL. Для кадровой частоты на Android требуется замер на телефоне.
