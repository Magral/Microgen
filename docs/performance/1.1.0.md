# 1.1.0 performance and stability checks

Measured 18 November 2026. Immutable baseline: stable 1.0.1 `b40c34e93dcba35a7fda0cea181c84803489e7ae`. Candidate: frozen preparation copies of release/1.1.0. The final native pass includes the fixed ribbon mesh for tendrils. Subsequent active-state projection/UI paging changes do not affect the game-render harness.

Godot 4.6.3, GL compatibility, 1280×720, Xorg dummy, Mesa llvmpipe software renderer; VSync-off is unsupported. Native runs were sequential. Short headless checks, file verification and documentation work overlapped some samples. A single pair cannot establish an overall speedup. These are desktop software-render results, **not Android FPS**. HUD/audio/controller autosaves and menus are outside the gameplay harness. Expanded body chambers are bounded to six visible vesicles but their maximum-cost scene is not separately benchmarked.

## What changed

- An active-state projection copies only active fields instead of first copying every archived family and then deleting that copy. Persistence still verifies all family records and retains its checked backup; large collections have a measurable write cost.
- Body pages instantiate at most eight cells rather than allocating every empty cell up to the full capacity. Stock pages instantiate at most three positions. A billion-cell boundary fixture opens the last page without building the intervening cells.
- Tendrils use a fixed 17-triangle ribbon with the same tapered boundary. A backwards strike can collapse its polygon axis; the old contour triangulation failed on that pose. The native regression and 22,816 mathematical poses pass. No organ-count, contour-resolution, enemy or effect cap was reduced.
- The performance runner now rejects ERROR/SCRIPT ERROR logs even if Godot exits zero. The initial candidate native pass exposed the tendril error and is excluded from the native table below; final repeated native logs are clean.

## Family save cost

Twelve checked saves and twelve family selections per size, representative fresh live checkpoints. Engine startup and family creation are excluded. Save verification/backup remain enabled. Same-family selection is a no-op in the one-family row. A slower filesystem/phone or larger checkpoint can cost more.

| Families | Save bytes | Save median/max ms | Switch median/max ms |
| --- | ---: | ---: | ---: |
| 1 | 17925 | 7.930/13.965 | 0.163/0.564 |
| 5 | 89349 | 53.677/64.168 | 47.870/63.557 |
| 10 | 178632 | 84.006/88.843 | 80.998/90.848 |

The ten-family save median changed from89.788 to84.006ms in this pair, while the five-family row became slower. The projection change removes unnecessary copying, but the pair does not justify a general timing improvement claim. Autosaves occur every12 seconds; large-family collections can still produce a visible write hitch. Splitting storage or background serialization needs separate migration/recovery work.
